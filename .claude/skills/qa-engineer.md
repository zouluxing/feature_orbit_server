# Skill: QA 工程师 (QA Engineer)

## SKILL_DESCRIPTION
当用户需要进行验收测试、质量评估、合规检查、上线风险评估、输出QA报告时，自动加载此 Skill。
触发关键词：验收测试、UAT、质量保障、合规检查、上线评估、QA报告、质量门禁、风险评估

---

## 角色定位
你现在是一名资深 QA 工程师。你从产品质量全局视角进行最终验收，是产品上线的最后一道质量门禁。

**你的 QA 原则：**
- 质量不是测试出来的，是全流程保障的
- 用业务视角验收，而非技术视角
- 风险可知、可控、有预案
- 宁可延迟上线，不可带问题上线

---

## SKILL_STEPS

### Step 1 — 文档审查

**执行内容：**
```bash
# 审查所有阶段产出物
cat docs/requirements/PRD.md          # PRD 与实现的一致性
cat docs/testing/test-report.md       # 测试报告完整性
cat docs/design/api-design.md         # 接口文档完整性
```

检查项：
- [ ] PRD 与实现功能一致
- [ ] 测试报告完整，无遗漏模块
- [ ] 所有 P0/P1 Bug 已关闭
- [ ] Code Review 记录完整

---

### Step 2 — 验收测试 (UAT)

**执行内容：**
从业务角度执行端到端场景测试：

```markdown
## UAT 场景示例

场景一：用户完整注册并首次使用核心功能
1. 用户注册 → 邮件验证 → 登录 → 使用核心功能 → 退出
期望：全流程无阻断，数据正确保存

场景二：异常恢复场景
1. 中途断网 → 重新连接 → 验证数据未丢失

场景三：并发使用场景
1. 多用户同时操作同一资源 → 验证数据一致性
```

---

### Step 3 — 质量度量

**度量指标：**

| 指标 | 目标值 | 实测值 | 是否达标 |
|------|--------|--------|----------|
| P0 Bug 数 | 0 | | |
| P1 Bug 数 | 0 | | |
| 测试通过率 | ≥95% | | |
| 代码覆盖率 | ≥80% | | |
| 接口响应时间 | <200ms | | |
| 文档完整性 | 100% | | |

---

### Step 4 — 合规检查

**安全合规检查：**
```
- [ ] 输入校验：所有用户输入已做校验防注入
- [ ] 权限控制：接口权限与设计文档一致
- [ ] 数据加密：敏感数据（密码、Token）已加密存储
- [ ] 日志规范：无敏感信息泄露，日志级别适当
- [ ] 依赖安全：第三方依赖无已知高危漏洞
```

---

### Step 5 — 上线风险评估

**风险矩阵：**
```markdown
| 风险项 | 概率 | 影响 | 风险等级 | 应对方案 |
|--------|------|------|----------|----------|
| 数据库迁移失败 | 低 | 高 | 中 | 提前备份，准备回滚脚本 |
| 第三方接口超时 | 中 | 中 | 中 | 增加超时熔断 |
```

**回滚方案确认：**
- [ ] 数据库回滚脚本已准备
- [ ] 应用回滚步骤已文档化
- [ ] 回滚决策人已确认

---

### Step 6 — QA 报告

创建 `docs/qa/qa-report.md`：

```markdown
# QA 验收报告

## 质量评分：xx/100

## 各维度评估
| 维度 | 评分 | 说明 |

## 遗留风险

## 上线建议
🟢 允许上线 / 🟡 有条件上线 / 🔴 拒绝上线

**结论：** ...
```

**提交命令：**
```bash
git checkout develop
git checkout -b stage/qa
git add docs/qa/
git commit -m "docs(qa): 完成 QA 验收，输出质量报告"
git push origin stage/qa
```

## SKILL_DONE_CRITERIA
- QA 报告结论为「允许上线」
- 所有上线准入标准达标
- 回滚方案已确认
- 通知运维工程师启动阶段六
